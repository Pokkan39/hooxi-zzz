## 0. 先看结论

### 0.1 重想要回答什么

不是“再找一个酷参考”，而是四件事：

1. **为谁**：第一用户是谁（只能有一个主用户）。
2. **30 秒路径**：根地址默认帮人完成什么。
3. **双层如何不抢戏**：PLAY 与正式档案谁是壳、谁是真相。
4. **视觉加在哪**：品牌光 / 工具光 / 电影光各管哪一屏。

### 0.2 建议工作假设（待你拍板，不是已定案）

| 项 | 建议假设 |
|----|----------|
| 主用户 | **补剧情 + 找片的观众**（定位书中的 A/B 合并为第一优先级） |
| 强辅助 | 追角色/阵营的关系导航（定位书 C） |
| 品牌滤镜 | Hooxi 创作者气质与幕后，不把站做成通用百科 |
| 总方案 | **S2 双门面**：轻量 Home 双入口；Default 仍是查档可达 |
| PLAY | **可跳过的沉浸 Mode**，不是内容门禁 |
| 视觉 | 一种“录像店基因”，两套用光；南孚只局部，AT 只方法，wiki 只结构 |
| 技术 | 静态可维护优先；大资产懒加载；WebGL 不进全局底座 |

### 0.3 明确不在本轮做的事

- 不改正式站主链路代码。
- 不新建/不改 demo 与原型页。
- 不把 V2 定位书整份作废（重想是**校准与取舍**，不是无根据推倒）。
- 不授权自动按三方对照施工。

## 1. 现行定位里：哪些是硬锚，哪些该重审

### 1.1 建议保留的硬锚（与 V2 一致）

来自定位书、重想时默认不推翻：

- 一句话：剧情**视频档案** + 角色**关系导航**；PLAY 可选。
- 核心任务：浏览、检索、关联、长期维护；从站内再回到视频平台观看。
- 价值五元组：找得到 / 看得懂 / 记得住 / 能分享 / 可维护。
- 不是：官方站、大全 wiki、数值站、模型站、纯 3D 秀、AT 复刻、社区。
- 根地址：轻量 DOM；不强迫 WebGL/大包。
- 正式档案：稳定 URL、剧透控制、来源、上下集与关联。

### 1.2 建议重审的张力（仓库现实）

| 张力 | 现象 | 设计含义 |
|------|------|----------|
| 多套平行宇宙 | tape-wall / scroll-world / cinematic-slice / tech-demos / prototype 等多条沉浸叙事 | 品牌故事未收敛，用户（与施工）不知“哪条算数” |
| 档案已强、门面未收 | catalog + enrichment + 主线剧透已可用 | 产品真相在档案层；门面不应另造内容模型 |
| 参考过多 | wiki / 南孚 / AT / 游戏 UI 同时在抢话语权 | 需要“一种基因 + 分区用光”，否则风格撕裂 |
| 角色页边界 | 印象/故事/来源 vs 养成/攻略 | 若主用户是找片，养成必须降级或折叠 |
| 栏目命名 | “角色故事” vs “角色与阵营” | 名称应反映关系导航，而不是故事专栏单一形态 |

### 1.3 重想原则（五条）

1. **默认路径服务主用户痛点**；沉浸是增强，不是税。
2. **正式 URL = 唯一内容真相**；一切 PLAY/原型只深链进档案。
3. **一屏一种主任务**：查、读、搜、泡气氛，不在同一屏全做满。
4. **静态可维护是产品约束**，不是临时技术债。
5. **无明确施工指令，分析与重想不得改正式站**（持续闸门）。

## 2. 用户价值重排

### 2.1 主用户假设

**第一用户：要补剧情、按版本/角色找到视频、又怕剧透的人。**

其成功瞬间：

1. 知道“从哪一集接到哪一集”。
2. 从安比/某阵营跳到相关成片。
3. 分享一条档案链接，对方打开是同一条。
4. 默认摘要不剧透。

**第二用户：追角色关系与世界观摘要的人。**  
成功瞬间：3 屏内回答“是谁、哪阵营、印象、有哪些相关影像”。

**品牌用户：为 Hooxi 而来的人。**  
成功瞬间：看得出是 Hooxi 的店与片单，不是绳网镜像；幕后/对谈有主场。

### 2.2 价值优先级（讨论用）

| 优先级 | 价值 | 含义 |
|--------|------|------|
| P0 | 找得到 + 看得懂 | 搜索、版本路线、关联、剧透 |
| P0 | 可维护 | 编辑器导出、结构化数据、Git 发布 |
| P1 | 能分享 | 稳定 URL、普通 HTML、可预览摘要 |
| P1 | 关系导航 | 阵营↔角色↔片 |
| P2 | 记得住（品牌） | 录像店语言、PLAY、扉页电影感 |
| P3 | 游戏式发现 | 抽带、邦布闲聊、彩蛋 |

P2/P3 不得破坏 P0。若资源冲突，先砍 P3 再砍 P2 的重度实现，不砍档案检索。

### 2.3 暂不服务（重申）

完整数值、全图鉴、社区投稿评论、模型下载、与剧情视频无关的作品集陈列、必须 AI 才能找到内容。

## 3. 信息架构（任务柜）

### 3.1 用户任务 → 栏目

```text
补剧情顺序     → 主线 / 版本时间轴
追人/阵营      → 角色与阵营（目录 + 详情）
回看活动       → 往期活动
看制作/对谈    → 幕后·对谈（Hooxi 主场）
快速定位       → 全局搜索
泡气氛/随便看  → HOOXI PLAY（可跳过）
维护内容       → 编辑器（内部）
```

### 3.2 建议主导航（讨论）

对外名称建议：

1. 主线剧情  
2. 角色与阵营  
3. 往期活动  
4. 幕后·对谈  
5. 搜索（可做头部常驻，不一定占一级 tab）  
6. 录像店 PLAY（视觉入口，文案避免像“唯一主页”）

### 3.3 内容对象与最小字段（设计层）

**片子 / 档案条目**

- 稳定 id、标题、类型、版本、章节  
- 无剧透摘要、剧透正文（受控）  
- 封面、播放入口（外链）  
- 角色 / 阵营 / 地点  
- prev / next / related  
- 来源、更新时间、spoilerLevel  

**角色**

- 稳定 id、名、阵营、属性标签（轻）  
- 一句话印象、故事摘要  
- **相关影像**（主线/活动/PV 链接，P0）  
- 来源  
- 养成/攻略：默认折叠或“待核验”，不占首屏  

**阵营**

- id、名、简介、成员列表、相关片/活动入口  

### 3.4 模块拼装原则（学 wiki 结构）

- 详情页 = 有序模块栈，不是一篇自由长文。  
- 每个模块只回答一个问题。  
- 空状态要说话（如幕后无稿：“等待制作信号”）。  
- 禁止为填满版面复制官网长文或攻略站数字。

## 4. 双层体验

### 4.1 分层定义

```text
壳层：HOOXI PLAY / 品牌落地
  └─ 气氛、发现、邦布导航（先规则检索，后可控 AI）
  └─ 输出：跳进正式档案 URL

核层：正式剧情档案
  └─ 唯一内容真相、可搜索、可分享、可编辑发布
```

### 4.2 根地址行为（S2 双门面）

首屏同时满足：

| 要求 | 说明 |
|------|------|
| 快 | 首屏不下载完整 3D/长帧序列 |
| 清 | 一句话定位 + 两个主动作 |
| 平权 | 「浏览档案」与「进入录像店」都明显；**档案不得小于装饰链接** |
| 安全 | 无自动声音；尊重减少动态效果 |
| 可跳过 | 店内任意状态可见“去档案” |

文案方向示例（非最终文案）：

- 标题：HOOXI  
- 副标题：绝区零剧情录像档案  
- 主按钮：浏览档案  
- 次按钮：进入录像店  

（若主用户确认更偏品牌秀，可对调主次，但必须保留双可达。）

### 4.3 PLAY 状态机（收敛用，不扩 scope）

定位书 A→H 仍可用，重想只加收敛律：

1. 所有“抽到的带 / 邦布结果”必须对应真实档案 id。  
2. 不做第二套仅存在于 3D 的隐式内容库。  
3. 进店失败（WebGL/网络）→ 自动落到档案，不白屏。  
4. 多原型仅能有一个“产品叙事候选”；其余标记实验，避免并列当真。

### 4.4 沉浸与档案的视觉交接

- 进档案后：**降 3D、升可读**。  
- 保留基因：档案编号、标签纸、少量暖/冷色、字体体系。  
- 不在正文背后继续高成本实时场景。

## 5. 视觉优先级

### 5.1 一种基因，三层用光

**基因（全站可复用的识别符号）**

- 凌晨录像店：店外冷、店内暖  
- VHS / 标签纸 / 档案编号 / 克制 CRT  
- 大字号标题 + 充足留白  
- 不要堆满霓虹故障扫描线  

**用光**

| 用光 | 用在哪 | 强度 |
|------|--------|------|
| 品牌光 | Home 落地、PLAY | 中高 |
| 工具光 | 列表、搜索、主线控制台、编辑器 | 中（清晰第一） |
| 电影光 | 版本序章、章节扉页、进店过程 | 局部高峰 |

### 5.2 参考站借法（与对照文档一致）

| 来源 | 借 | 不借 |
|----------|------|
| 官方 wiki | 模块化详情、频道式 IA、结构化摘要 | 整站皮、养成大全、原文搬运 |
| 南孚 | 局部卷动电影感、帧序列 scrub 思路 | 全站超长一页、品牌物料 |
| Active Theory | 暗场、留白、纵深、卡片聚焦方法 | Hydra/Shader/字体/Logo/案例 |

### 5.3 页面级视觉优先级（讨论）

| 页面 | 第一优先级 | 第二 | 明确降级 |
|------|------------|------|----------|
| Home | 双入口理解 | 品牌气质 | 自动大资产 |
| 主线 | 版本路线与筛选 | HUD 氛围 | 背景 3D |
| 角色目录 | 搜索与阵营过滤 | 立绘阵列 | 复杂视差抢点击 |
| 角色详情 | 身份 + 相关影像 | 印象/故事 | 养成首屏 |
| 阵营 | 成员可点 | 简介 | 空装饰 |
| 活动/幕后 | 时间与条目可读 | 专题气息 | 无内容时装满特效 |
| PLAY | 空间可读 + 可逃逸 | 互动趣味 | 劝用户别去档案 |

### 5.4 动效政策

- 默认尊重 `prefers-reduced-motion`。  
- 滚动叙事不 `preventDefault` 锁死原生滚动（若未来做长页）。  
- 动效服务状态变化（进店、抽带、聚焦），不服务无意义循环闪烁。

## 6. 总方案对照（供拍板）

### S1 档案本尊

- Home 几乎是导航枢纽；PLAY 极弱。  
- 适合：维护力量极紧、主用户极工具向。  
- 风险：品牌记忆变薄。

### S2 双门面（建议作为讨论底稿）

- Home 双门平权；档案为核，PLAY 为壳。  
- 适合：现行 V2 与仓库现状。  
- 风险：两套 UI 若基因不统一会像两站。

### S3 长片叙事站

- 以卷动电影讲版本故事为 Home 主体验。  
- 适合：单次战役级专题。  
- 风险：检索与更新成本；易偏离“视频档案”使命。

**建议：整站骨架 S2；S1 为性能/工期底线；S3 仅作“某版本特辑页”可选，不取代根 IA。**

## 7. 与现行完成度的设计含义（不施工）

已具备（设计上应视为核层资产）：

- 静态多页档案、编辑器链路  
- 主线版本/筛选/剧透  
- 代理人花名册与 enrichment 摘要  
- 多条 PLAY/技术隔离实验  

设计结论：

- **核层优先打磨信息秩序与命名**，而不是再开一条新技术demo。  
- **壳层先选一条叙事收口**（店门→柜→CRT→档案），其它实验归档。  
- **英雄区若将来增强**，优先可降级的短视频/少量帧序列，不先上全站 WebGL。

## 9. 一旦定案后的建议落地顺序（仍须另下施工令）

> 下表是**设计实施顺序建议**，不是本任务授权。

1. 冻结 IA 与命名（导航、栏目、空状态语气）。  
2. Home 双门信息结构（先内容与文案，后特效）。  
3. 角色详情模块秩序（相关影像 P0，养成后置）。  
4. 主线路线可读性（版本轨 + 上下集）。  
5. 全站基因（编号、标签、色、字体）统一到档案层。  
6. PLAY 只收口一条链路并对齐深链。  
7. 局部电影光（序章/进店）按需，过闸门再动正式站。

## 10. 验收标准（设计是否想清楚）

满足以下可认为“重想阶段可收口为定案候选”：

1. 能用一句话说清主用户与 30 秒默认路径。  
2. 能画出任务柜 → 栏目 → 页面主模块。  
3. 能说明 PLAY 与档案谁是真相、如何跳转。  
4. 能说明三层用光各用在哪些页。  
5. 能列出不做什么（含养成深度、全站 WebGL、整站南孚化）。  
6. 仍不触碰正式站代码，除非另附施工指令。
